# Spring cleanup audit

## Packaging, plan projection, and schema review — 2026-10-18

The desktop build now stages compressed copies of the catalog images. Original 255 MiB PNG assets remain available for image maintenance, while packaged JPEGs use about 26 MiB. The source catalogs and attribution hashes are not rewritten. The Windows and Linux build scripts bundle only the staged catalog tree. Android packaging remains unchanged in this pass.

Shopping fetches upcoming plans only while its tab is open, so ordinary Week navigation does not repeat an unbounded plan read. `PlanStore` labels plans from cached raw localized recipe rows; it avoids constructing every full recipe DTO and querying ingredient translations just to display plan titles. Shopping uses one persistent upcoming draft and derives planned recipe bought status from checked ingredient keys and a saved recipe/servings signature.

The SQLite schema was reviewed for third normal form. Ingredient IDs, localized translations, and prices already have separate tables with foreign keys and unique natural keys. The existing `ingredient_price` row represents one ingredient, period, and unit; its amount and optional reference basis depend on that full key. There is no duplicated recipe or plan data in SQLite. A table rewrite would add migration risk without removing a 3NF violation, so this pass leaves existing SQLite files intact. The new bought status lives with shopping choices in `shopping.json`.

## Package and lint follow-up — 2026-10-18

The retired `routes` and frontend `api` directories contained only ignored bytecode caches. They and the old feature package directories were removed. Backend behavior now sits in a `stores` package, while the app-facing planner and shared validation sit in `core`; entities and repositories keep their existing storage roles. The shared ID pattern no longer makes the ingredient store import the recipe store. Development and quality commands write Python bytecode under ignored `build/python-cache` so routine runs do not recreate source-tree cache directories. Ruff now checks import order, common bug patterns and simplifications, and stale lint suppressions; the frontend import blocks and three small control-flow cases were cleaned up.

## Local service follow-up — 2026-10-17

After removing the loopback server, the app still called its local service `client` and checked whether fixed service methods existed before connecting Shopping writes. The UI now calls it `planner` and binds those methods directly when startup succeeds. The startup-error view keeps Shopping writers unset, and the UI tests use a missing planner to exercise that state. The backend also retained an unused method that derived Shopping ingredients from every Week meal; it was removed because Shopping imports only explicitly selected meals. The security review now describes the current local boundary instead of presenting retired HTTP controls as active.

`loc-rank --top 30 src` showed the largest production files remain feature-focused: `RecipeBrowser.py` (379 lines), `AdminPanel.py` (344), `RecipeStore.py` (340), `ShoppingDraft.py` (337), and `CookingPlannerApp.py` (307 before this pass). This pass found no additional shared responsibility that justified another layer or file split. The direct service and UI smoke checks cover the current architecture.

Use `loc-rank --top 20 src` to identify files worth inspecting. Line count alone does not justify splitting a cohesive feature. An earlier cleanup moved shell and tab construction from `CookingPlannerApp.py` to `AppShell.py`, and shopping draft validation and atomic file handling from `ShoppingDraft.py` to `shopping/persistence.py`. Those responsibilities now have one clear home while the public behavior and JSON format stay the same.

The performance pass coalesces rapid refresh requests so only the current request and the latest pending state consume worker time. Repeated clicks on the active tab keep its existing widgets; returning to Admin reuses its loaded catalog until an explicit refresh or edit. Scheduled list, row, and search work is cancelled when its panel is replaced. Recipe search text is built once when the browser opens instead of being rebuilt for every filter change. Catalogs remain read only and user drafts still save synchronously for crash recovery.

`test_ui_flow.py` is still the largest file because its tests share a live Kivy fixture and exercise interactions across features. `RecipeStore.py`, `ShoppingDraft.py`, and several editor views remain substantial but each owns a cohesive feature. Split them only when a specific responsibility or bottleneck calls for it. Generated `build/` and `dist/` contents, virtual environments, and Kivy caches are ignored; they are not source files.

The ingredient selection audit used `loc-rank --top 20 src`. Recipe editing now loads catalog ingredients only when Admin opens. Its chooser shows the first page immediately and creates at most 40 option widgets at a time; filtering is optional. The chooser lives in `IngredientPicker.py`, leaving recipe form state in `AdminPanel.py`. The old recipe ingredient text search, generated ingredient IDs, and recipe-save writes to catalog translations were removed. Recipe saves require existing catalog IDs and take localized ingredient names from SQLite. New ingredients and translations are managed in the ingredient catalog.
