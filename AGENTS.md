# Cooking Planner working guide

Read `README.md`, `docs/ARCHITECTURE.md`, `docs/CODE_QUALITY.md`, and `docs/PYTHON_MIGRATION.md` before changing behavior. Keep recipes and plans in feature-owned Python backend modules under `src/backend`. HTTP controllers live in `routes`; services own behavior, repositories own persistence, and mappers convert external data only when its shape differs. Kivy views under `src/frontend` use only the HTTP client; the launcher owns the backend thread. Recipe catalogs use `data/recipes_<language>.json` and are read only; preserve every catalog and existing meal plan on failures or upgrades. Keep writable plans and client settings under the configured user data directory.

Run `make quality` for syntax, Ruff, tests, and separate 60% Python frontend/backend line coverage floors. For desktop changes, also run a real Kivy event-loop smoke on a machine with a display; check normal and 200% UI scaling before calling the UI verified. `make dev` opens the Python app without a distribution build. `make compile-linux` and `scripts/build/windows/build-windows.ps1` own the native packaging workflow; do not claim either build verified without running it on that platform.

Do not add empty layers simply to match a package checklist. Keep HTTP routes grouped by feature and keep admin routes separate from public routes. Name production files that define a class after that class in PascalCase; keep `test_*.py` for test discovery. Add a mapper when an external recipe format actually differs from the internal recipe DTO; add utilities only for code shared by multiple features.
